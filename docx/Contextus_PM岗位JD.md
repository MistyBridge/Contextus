# 产品经理 JD — Contextus

> 2026-08-14 · 远程 / 兼职起步（可转全职）· 技术型产品经理（devtool）

## 一、关于 Contextus

Contextus 是一个面向 AI Agent 的「会话状态运行时」：用户与 AI Agent 的每一轮交互自动成为一个 git commit（代码 + 对话 + 审计日志的世界快照）；会话呈树形结构——任意历史节点可分支（多世界线并行）、可回溯、可双向追溯（代码提交 ↔ 产生它的对话）；一套版本化规则全局生效。

MVP 已全部完成并经真实窗口验收（命令行 + TUI + 完整测试体系）。团队现状：产品负责人（创始人）、核心开发、前端工程师（已到位，负责炫酷的树形 UI）。**现在需要一个 PM，把项目从「能用的 MVP」推向「有人用的产品」。**

## 二、岗位定位

**技术型产品经理（Developer Tool）**——不是画原型的人，前端工程师负责 UI；你是**方向、内容与质量**的负责人：

1. **产品方向与需求管理**：把路线图变成可执行的、带验收标准的需求文档
2. **技术内容与开发者布道（DevRel）**：文档、Demo、教程、社区——devtool 的命脉
3. **数据与验收负责人（Benchmark / QA Owner）**：维护验收体系，对发布签字

## 三、具体职责

### 1. 产品方向与需求管理

- 维护产品路线图（Phase 2 已有明确候选池，见下），做优先级决策并给出理由
- 按 Contextus 的**方案文档文化**产出需求：每个功能的需求文档必须包含——问题、方案、验收断言、风险（参考仓库内 `docx/Contextus_MVP技术方案.md` 的范式，这是本项目最成功的协作方式）
- 与核心开发对齐技术可行性，与前端工程师对齐呈现方式，守住「最小内容」原则（不为做而做）

**Phase 2 候选池（已有共识的方向）**：重建分支（压缩历史链上下文 → 新树 → 挂 skill/mcp 基础上下文之下）、scrub 历史清理、记忆目录版本化（Experience Chunk 载体）、完整 Chunk 体系与 Context Resolver（自动选择配置边界节点）、Context Merge、REST API 与多 Agent。

### 2. 技术内容与开发者布道

- **把概念讲清楚**：这是本产品最大的难点——「世界线」「回溯即分叉」「一轮一 commit」「看不到但生效的规则」。立项书里的概念图（a b c d → 回到 b 开分支 → a b e f）是现成素材，把它变成文档、教程、Demo 视频
- 内容资产：官方文档、3 分钟上手视频、真实场景教程（如「用 Contextus 管理一个量化策略的多次方案尝试」）、发布公告
- 社区运营：GitHub（issues/讨论）、开发者社区（Hacker News / Reddit / V2EX 等）的发布与回应
- 收集真实用户反馈，形成产品需求输入

### 3. 数据与验收负责人（Benchmark / QA Owner）

- **维护验收体系**（已建立，你是守门人）：
  - 九场景验收清单（T1~T9，含配置边界分支、同步分支、维护操作等）
  - 七项硬指标（1:1 绑定、回放协议、工作区干净、规则 O(1) 更新、升级回归、性能继承、改必审计）
  - 回放协议（1000 会话抽样校验 + 50 真执行）
  - 升级回归入口（`upgrade-check.sh`——Claude Code 每次升级必跑）
- 对每个版本发布签字；建立「发布清单」
- 用数据说话：token 成本、命中率、场景通过率——定期输出产品健康报告
